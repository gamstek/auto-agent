# 设备能力与持久化自动化：设计与开发路线

状态：**设计基线，分阶段实施中**。P0–P4 的源码实施情况见 [实施状态](./progress.md)；工作流、定时与常驻服务仍待开发。下表保留设计时起点，不能把全部目标当成当前版本能力。

## 目标

1. 重构 `device-automation`：Skill 承载方法、任务规划和流程指导，真实设备能力通过 MCP 提供。
2. 桌面增加独立“仪器”页面，首先展示 Climber 的实际连接、就绪和当前批次状态。
3. 增加模型之外的持久化执行器，为长时间等待、断点恢复、定时运行和跨设备调度提供基础。
4. 聊天、仪器页面和工作流共用设备配置、状态来源及操作仲裁，避免形成三套独立设备控制逻辑。

## 当前实现与目标的差距

本表记录设计时的起点；最新实现以 [progress.md](./progress.md)、现行配置示例与 `llm.txt` 为准。

| 领域         | 当前实现                                         | 目标                                                          |
| ------------ | ------------------------------------------------ | ------------------------------------------------------------- |
| Agent 工具   | `src/tool/index.ts` 注册六个固定工具             | 保留内置工具，增加受控 MCP 工具目录和动态调度                 |
| Climber      | Skill 的 `scripts/climber.js` 直连厂家 HTTP      | 独立 `climber-mcp`，宿主经统一设备操作入口调用                |

| 自动化       | `scripts/automation.js` 仅模拟外部流程服务       | 新增宿主持久化流程；外部流程服务接入仍单独建模                |
| 执行审计     | 脚本先记录 intent，未知效果阻断依赖步骤          | 将同等语义延伸至 MCP 写操作与工作流步骤                       |

| 数据所有权   | SQLite 数据目录由单个后端独占                    | 初期保留单进程执行器，服务模式也只有一个数据所有者            |
| 桌面         | 聊天、设置、悬浮助手；无仪器页                   | 增加只读仪器页，再按阶段展示工作流进度                        |
| 进程生命周期 | 关闭桌面退出其管理的后端，忙时拒绝退出           | 保留交互模式；以后明确增加独立常驻服务模式                    |

## 已确定的设计决策

- Skill 指导“怎么完成任务”，MCP 封装“设备可以做什么”；MCP 本身不是工作流调度器。
- 宿主先实现通用 MCP 客户端，不把 Climber HTTP 专用调用伪装成通用 MCP 接入。
- 直接查询设备状态不要求先加载 Skill；SAM 资源和脚本仍遵循现有当轮 Skill 加载规则。
- 仪器页不调用模型，不直连厂家 API，不在 WebView 中运行 MCP。
- 第一版仪器页只读，不提供登记、启动、停止按钮。
- 第一条真实宿主流程为固定版本的 `climber-batch`，不先做任意 DAG 编辑器或任意代码执行平台。
- 不确定外部写入不自动重试。MCP 断连、软件取消和进程退出均不是设备停止的证明。
- 对话结束、设备命令受理、仪器运行完成、结果文件可用是不同事实。
- 共享 `~/.auto-agent/config.json`；新增设备配置不能回退到独立桌面配置，也不引入旧桌面配置迁移。
- 第一阶段持久化执行器与现有后端共享同一个 Store 和生命周期；不增加第二个直接操作同一 SQLite 的进程。
- 只有独立常驻后端实际可用后，才能向用户承诺“关闭桌面仍继续执行”。

## 两种流程必须区分

现有 [自动化接口契约](../../corax/skills/device-automation/references/automation.md) 描述的是：外部自动化控制系统拥有完整流程，Agent 选择其已有模板并提交一次运行。新宿主流程不能悄悄改变该契约。

| 执行主体             | 宿主负责                                     | 外部系统负责                       |
| -------------------- | -------------------------------------------- | ---------------------------------- |
| `executor: host`     | 已实现步骤的依赖、资源预留、调用、等待和恢复 | 各设备自己的任务执行               |
| `executor: external` | 提交外部流程、关联其运行 ID、跟踪与核对      | 整套流程的内部步骤、仪器调度与联锁 |

外部流程运行期间，宿主不能同时拆开它去直接控制内部仪器。部署中必须登记其涉及的设备范围；范围不明确时，不开放可能冲突的直控写入。

`automation.js` 保持模拟标识，只用于开发与评测，不能自动成为真实工作流执行器的实现或状态来源。
