# 历史读取性能诊断：Corax 0.1.0

## 结论

当前安装依赖 `@coraxjs/core@0.1.0` 的本地 Workflow 存储在获取流尾索引时逐个打开 chunk 文件；原生 HTTP `follow=false` 链路会重复获取尾索引。负游标减少返回的事件正文，却没有消除与历史总事件数成正比的文件访问。仅修改 UI 渲染窗口、尾部事件数或投影调度不能根治冷打开等待。

本结论以安装包的只读实现检查及隔离服务的文件访问计数为依据，不依赖邻接 Corax 源码仓库，不修改安装的 SDK 或用户历史。

## 可复现的链路

检查的文件相对 `node_modules/@coraxjs/core/dist/src/`：

1. `corax-channel/request.js` 的 `createSessionStreamResponse` 调用 `session.getEventStream({follow:false,startIndex})`，并另外等待 `session.getStreamTailIndex()` 才返回响应。
2. `execution/session-event-stream.js` 的 `streamSessionEvents` 在 `follow=false` 时也调用 `readSessionStreamTailIndex()`，据此确定负游标的绝对位置及停止位置。
3. `compiled/@workflow/world-local/index.js` 的 `streams.getInfo` 枚举、排序 chunk 文件，并串行读取每个文件的第一个字节，检查 EOF 标志。每次标志检查包含一次文件打开、读取和关闭；没有直接命中持久尾索引。
4. 同文件的 `streams.get` 另外枚举 chunk 目录，然后读取所请求区间的正文。因此取最后 N 个事件仍包含整个流的索引扫描成本。

## 文件访问计数实测

使用之前通过标准 `corax build/start` 和本地假模型生成的 1、8、24 轮隔离会话；重新启动隔离服务，只发送 GET 历史请求。不调用模型、不发送新消息、不访问用户会话。临时 Node preload 仅统计 `streams/chunks/` 下的 `fs/promises.open`、`readFile` 和 `readdir` 调用，返回原方法结果，不替换存储实现，不输出文件路径或内容。

| 历史事件总数 | startIndex | 返回事件数 | 文件打开次数 | 正文读取次数 | 目录枚举次数 |
| -----------: | ---------: | ---------: | -----------: | -----------: | -----------: |
|          457 |        -64 |         64 |          914 |           64 |            3 |
|          457 |       -128 |        128 |          914 |          128 |            3 |
|          457 |          0 |        457 |          914 |          457 |            3 |
|          457 |        457 |          0 |          914 |            0 |            2 |
|          153 |        -64 |         64 |          306 |           64 |            3 |

|           20 |        -64 |         20 |           40 |           20 |            3 |

即使请求已知尾部之后的空增量，也发生两遍完整扫描。首次测量 457 个事件的 -64 请求，响应头约 3018ms、总计 3045ms；重复启动和读取后同项约 80ms/108ms。访问计数不变，耗时会受到文件系统缓存、系统负载等影响，不能把较快的重复测量当作冷启动保证，也未证明首次较慢具体由哪种系统因素造成。

## 与实际症状的对应

安装版中，一个只有 13 轮的真实会话包含 26,243 个事件，大量为逐段文本、思考和工具参数。其尾部 512 个事件读取曾测得约 3.5 秒，全量读取约 9.6 秒；一次完整 UI 跟踪在约 12 秒时才开始投影，约 13.2 秒完成。投影并不是这次等待的主要部分。

前端窗口扩大、已完成回复预览与任务调度优化只能减少部分等待；不能将其描述为已经修好底层历史读取。此前的隔离假模型只有数百个事件、每轮事件较少，未覆盖这种实际规模，因此不足以作产品验收依据。

## 根治方向与边界

修复应通过 Corax/Workflow 的受支持版本提供：

- 本地流尾索引及有界区间读取不应逐事件打开所有历史文件；可维护由原生存储拥有的尾信息/索引，保证并发写入、崩溃恢复、EOF、清理和历史兼容性。
- 同一次有限流读取应共享固定尾边界，避免 HTTP 层与流读取层分别扫描，且响应头和正文使用一致的边界。
- 如要避免打开会话时全量回放，还需原生完整会话状态快照与事件游标配套，覆盖跨轮次任务和待输入状态。
- 验收应覆盖至少数万事件的冷、热读及空增量；同时检查文件访问次数、响应头时间、正文时间和最终状态正确性。

应用侧不直接读取或改写 Workflow 私有文件，不补建持久聊天数据库，不用尾部片段授权发送，也不直接手改 `node_modules`。当前性能问题尚未完全解决；再次提供安装包前，应在相同慢会话上证明改善，而不是仅依据单元测试或小样本构建成功。

## 已批准的 pnpm 补丁

用户明确批准通过 `pnpm patch` 验证和交付局部修复。补丁固定为 `@coraxjs/core@0.1.0`，由 `pnpm-workspace.yaml` 的 `patchedDependencies` 与共享锁文件关联，文件为 `patches/@coraxjs__core@0.1.0.patch`。

本轮保守修改 `streams.getInfo`：仍使用原来的文件名快照、扩展名/tag 选择和单字节 EOF 检查，每批至多并发 32 个检查。结果按原始文件顺序处理，遇到第一个 EOF 即返回；EOF 前的错误正常抛出，EOF 后并发检查产生的错误不改变原有结果。返回前等待本批操作完成，不遗留未处理 rejection 或文件句柄。没有缓存跨请求尾索引，没有改写、迁移存储格式，也没有假定 EOF 永远是最后一个文件。

发布包的 world-local 文件经过压缩，补丁先将该产物格式化以定位修改；因此 diff 包含较多纯格式变化。实质行为修改只有 `getInfo` 调用新的 `stream-info-batched.js`，未修改模型、任务运行、消息受理或原生写入流程。应用代码继续只使用公开 API。

### 补丁性能验证

26,243 个隔离 chunk 文件，同一机器交替执行原串行检查与 32 路检查，各 3 次：

| 检查方式   | 第 1 次 | 第 2 次 | 第 3 次 | 中位数 |
| ---------- | ------: | ------: | ------: | -----: |
| 串行       |  3093ms |  2813ms |  2835ms | 2835ms |
| 并发 32 路 |   327ms |   301ms |   313ms |  313ms |

返回的 `tailIndex=26242, done=false` 完全一致。这里测的是尾索引检查，不是 UI 首屏，也不是冷磁盘保证；文件访问总数仍为 O(N)。标准 Corax build/start 隔离服务也成功运行，457 事件样本读取最后 128 个事件的中位耗时约 55ms，修补前样本约 98ms；两次服务运行的缓存条件并不完全相同，仅作集成佐证。

### 验收和维护

- `tests/node/corax-stream-patch.test.ts` 验证空流、批次边界、错误顺序、第一个 EOF、并发上限、操作排空，以及实际本地流写入/关闭/关闭后追加/重新创建 world 的行为。
- `pnpm install --frozen-lockfile` 必须能重现补丁；`prepare-runtime.ts` 和安装包验收要求随包 helper 存在。
- 第一轮仅并行化扫描；下一节记录后续经过单独验证的请求内去重。两项优化都没有消除全部历史读取，不能宣称从 O(N) 改成 O(1)。
- 上游发布等价修复后，移除 `patchedDependencies` 与补丁文件，通过 pnpm 更新锁文件，重复相同契约及慢会话测试。

## 第二轮：有限读取共用固定尾边界

用户确认进一步合并重复尾查询。补丁在 `follow=false` HTTP 请求入口建立 `AsyncLocalStorage` 作用域，使 `readSessionStreamTailIndex` 的两个调用共享同一个 Promise。`readSessionEventHistory` 在创建流时捕获这个 Promise，后续 pull 即使在其他异步上下文执行，也使用同一个尾边界；负游标解析、停止位置与响应头保持一致。新请求、新会话和实时订阅不复用这个尾值，错误只影响原请求，后续请求可以重新读取。

Nitro 路由与 registry Workflow runtime 可能各自载入 helper 的副本，因此仅将 ALS 容器放在进程全局的专用 Symbol 中；尾值仍只存于请求作用域，没有跨请求 TTL 或持久索引。实际构建验证曾发现只用模块局部 ALS 时无法去重，已通过跨副本契约测试和原生 HTTP 文件计数确认修正。

标准 build/start 服务的隔离会话计数：

| 历史事件数 | 请求        | 原文件打开次数 | 共享边界后 | 返回事件数 |
| ---------: | ----------- | -------------: | ---------: | ---------: |
|        457 | 最后 64 个  |            914 |        457 |         64 |
|        457 | 最后 128 个 |            914 |        457 |        128 |
|        457 | 全量        |            914 |        457 |        457 |
|        457 | 空增量      |            914 |        457 |          0 |
|        153 | 空增量      |            306 |        153 |          0 |
|         20 | 空增量      |             40 |         20 |          0 |

有正文时目录枚举从 3 次降到 2 次，空增量从 2 次降到 1 次。尾索引和响应事件计数一致。该结果证明去除了重复扫描，不代表实际桌面延迟必然减半；仍需在慢会话上分别记录首屏和完整就绪时间。滚动追加消息仍由应用层 `useMessageWindow` 管理，每次 20 条，补丁不改变这项交互。
