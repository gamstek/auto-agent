# Wiki 重构设计：统一资料库与可扩展解析

状态：目标设计，第一阶段已实现。已实现的配置、接口、原件核验结果与后续范围见 [wiki-progress.md](./wiki-progress.md)。本文包括尚未实现的资料包、页面维护和管理接口，不能直接把全部示例当作现有配置。

## 1. 核心决策

**Wiki 是通用的本地资料检索服务。用户添加资料，系统解析、索引并提供有来源的搜索和阅读。**

- 一个资料入口：文件、目录或已发布资料包。
- 一条处理流程：发现 → 固定内容版本 → 解析 → 生成检索单元 → 发布索引。
- 一套模型工具：发现资料范围、搜索、阅读。不按“推荐知识”和“模板参考”分两套查询。
- 通用核心不认识仪器产品、实验模式、材料、气体或模板字段；这些由解析扩展提供。
- 默认本地处理，不依赖模型。模型摘要/结构化提取是显式启用的增强步骤，不是资料可用的前提。
- Skill 负责如何使用领域资料，Wiki 提供证据；两者不互相充当身份或权限系统。

这不是把两个目录改名后继续保留两套实现，也不是把所有文件统一送给模型。

## 2. 现状问题与依据

| 现状                     | 源码/资产                                                                   | 问题                                                  |
| ------------------------ | --------------------------------------------------------------------------- | ----------------------------------------------------- |
| 文档编译成推荐 JSON      | `wiki/sources/`、`wiki/knowledge/recommendations.json`、`src/wiki/build.ts` | 文档要先经过模型才可检索，人工还要维护引用/哈希一致性 |
| 历史模板单独形成 SQLite  | `wiki/indexes/library.sqlite`、`src/wiki/file-index/`                       | 同为资料，却走另一套存储、身份和更新机制              |
| 两种来源配置与更新动作   | `wikiRoots` / `wikiIndexRoots`，`--wiki-update` / `--wiki-index`            | 用户必须了解实现内部分类才能添加资料                  |
| 同一个工具有两种语义     | `query` 是推荐，`search/read` 是模板                                        | 名称看似通用，行为由业务分类决定                      |
| 专用字段进入公共协议     | `file-index/schema.ts` 的 product/gas/labType 等                            | 增加新领域需要修改通用工具、API 和索引模型            |
| 普通知识查询重新读取源树 | `sources.ts`、`queryWiki()`                                                 | 查询与扫描耦合；一个来源变化会使整体推荐不可用        |
| 模板库与外部索引切换     | `Wiki.files`                                                                | 配置外部模板目录后，内置快照不再按同一机制参与检索    |
| Wiki 索引依赖聊天 Store  | `Wiki(config, store.db)`                                                    | 资料服务无法真正独立复用，存储迁移也与会话混合        |

用户已提供外部案例库原件。只读核验确认旧 `library.sqlite` 的 178 条记录均有对应原件且 SHA-256 一致，迁移可从原件重建。发布后的离线资料仍须区分“迁移时已核验”与“当前外部原件仍一致”，不能把一次核验当作永久有效。原件清单和验证结果见实施进度文档。

## 3. 用户如何添加与使用

### 3.1 一次添加，不要求用户选择内部存储类型

桌面的“资料库”提供：添加文件、关联文件夹、导入资料包。

- 添加文件：复制到应用管理的资料区，保留原文件名和导入来源。
- 关联文件夹：只读关联已有目录，不移动原件。用户原来的子目录组织保持不变。
- 导入资料包：验证清单与文件哈希后登记为同一种资料来源；资料包可以不含原件，但必须明确标注。
- “资料集”只用于组织、筛选和访问范围，例如团队手册、个人资料，不决定解析流程。一个资料集可混合多种格式。

添加后显示处理数量、支持/不支持的格式、失败原因和索引版本。用户不需要创建 `knowledge/` 或手动维护 SQLite、JSON 和引用哈希。

添加来源属于明确操作，可直接安排本地索引；应用启动和聊天查询不扫描文件夹、不启动模型提取。文件夹的后续变更第一期由“刷新”触发，自动监听另行实现。

### 3.2 目标配置示例

```json
{
  "wiki": {
    "sources": [
      {
        "id": "manuals",
        "type": "directory",
        "path": "./资料",
        "collection": "team",
        "include": ["**/*"],
        "exclude": ["**/.git/**"]
      },
      { "id": "starter", "type": "bundle", "path": "./packages/starter.wiki" }
    ],
    "parsers": ["builtin.text", "builtin.markdown", "builtin.json", "sam.reference"],
    "enrichment": { "enabled": false }
  }
}
```

约定：相对来源路径仍以共享配置文件目录为基准；应用管理的导入来源由资料服务登记，不让桌面把 dataDir 下的内部路径反复写回配置。解析器 ID 必须由发行应用注册，配置不能指定任意模块路径。`sam.reference` 是领域扩展名称，不是核心分支条件。

`wikiRoots` 和 `wikiIndexRoots` 最终由统一来源定义替代，不能长期保留两套路由策略。切换时提供显式转换报告，保留原配置备份；不在启动或聊天时猜测并迁移。

### 3.3 查询体验

用户问问题 → Agent 搜索资料 → 按命中 ID 阅读对应片段 → 引用来源回答。需要领域解释时加载相关 Skill。

搜索结果统一显示标题、来源、命中片段、内容版本、解析状态和引用位置。模板的产品、版本、单位等作为扩展字段显示；文档不需要填充一组无意义的仪器字段。

## 4. 原始资料与派生产物的存放

用户看到一个资料库，物理上仍须区分原件和派生索引。索引可以重建，不能覆盖或修改原件。

### 仓库中的可发布资料

```text
wiki/
  README.md
  starter/
    wiki.json             资料包清单、许可证/来源、文件清单
    documents/            原始资料，可按用户需要分子目录
```

资料包构建产生统一发布物，例如 `dist/wiki/starter.wiki`。源码目录不再要求人工维护 `recommendations.json` 和专用 `library.sqlite` 两条生产链。发行构建将发布物嵌入二进制；离线加载不需要原始开发目录。

当前历史模板库从已核验原件重建统一资料包并保留完整 provenance。对于未来确实缺少原件的导入快照，才采用明确标注的“仅派生内容”导入路径。旧资产在新包覆盖、字段和引用验收前保留。

### 运行时

```text
dataDir/wiki/
  wiki.sqlite             来源、文档、版本、解析单元、FTS、构建任务
  objects/sha256/...      管理型导入原件/固定版本内容，内容寻址
  bundles/<id>/<digest>/  已验证、不可变的内置或导入资料包
  staging/<jobId>/        尚未发布的处理内容
```

关联目录保留在原处。索引保存可复现引用所需的解析文本/结构化单元，原始大型二进制是否保留由来源策略明确指定。第一期不在这里写会话、运行审计或设备状态。

资料数据库由 Wiki 服务拥有生命周期，应用组合层注入 Wiki 能力；不再通过 `Agent Store.db` 建表。仍遵守整个 dataDir 的单进程独占，不新增绕过所有权的第二个写进程。

## 5. 通用数据模型

| 对象            | 必需信息                                                     | 说明                                                           |
| --------------- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| Source          | id、type、locator、collection、策略、启用状态                | 来源身份不直接等于本机绝对路径哈希                             |
| Document        | id、sourceId、relativePath、title、mediaType                 | 同一来源内的逻辑文档，更新内容不改变身份                       |
| DocumentVersion | id、documentId、contentHash、bytes、observedAt               | 不可变内容版本；路径迁移默认产生新身份，不猜测重命名           |
| Representation  | id、versionId、parserId、parserVersion、optionsHash、state   | 同一原件的解析结果，可为 text/structured；版本与配置参与缓存键 |
| Unit            | id、representationId、text、locator、attributes              | 搜索与阅读的最小定位单元；划分版本纳入身份计算                 |
| Derivation      | id、输入版本、transformId/version、模型/提示词版本、证据引用 | 可选摘要/结构化提取，不冒充原文                                |
| IndexGeneration | id、来源版本集合、构建参数、publishedAt                      | 一个可查询的已发布视图                                         |
| BuildJob        | id、scope、phase、progress、error、cancelled                 | 资料维护任务，不混入 Agent run 或未来工作流                    |

引用至少含 `documentId + versionId + unitId/locator`。定位类型支持行区间、页码、表格单元格、JSON Pointer；不能把所有格式硬塞成“文本第几行”。

版本化数据不无限保留：当前已发布版本和明确保留的版本受保护，清理按照引用与保留策略执行；过期引用返回 `version_unavailable`，不悄悄跳转到最新内容。历史对话仍保留当时的引用和有界片段。

### 5.1 通用与领域字段的边界

核心属性限于标题、类型、标签、来源、时间、语言、解析状态等通用字段。扩展字段具有命名空间与 schema，例如 `sam.product`、`sam.clientVersion`，由插件声明类型、单位、可检索/可筛选性和显示信息。

- 核心实现字段类型校验、索引及比较操作，不认识字段的业务含义。
- 未注册字段不能作为筛选条件；字段名不能拼接成 SQL。
- 历史 labType、启用状态、原始单位与解释不确定性由 SAM 解析器完整保留，不因通用化而丢失。
- 模型派生字段与确定性解析字段必须注明不同 provenance；优先级不能只靠一个混合置信分数决定。

## 6. 解析扩展与增强

### 6.1 分清格式解析和领域解释

格式解析器把原件转为可引用单元；领域扩展在同一协议内提供专属结构和筛选字段。单纯支持文件扩展名不等于理解业务语义。

建议接口：

```ts
interface DocumentParser {
  id: string;
  version: string;
  mediaTypes: readonly string[];
  fields: readonly FieldDefinition[];
  supports(input: FileDescriptor): boolean;
  parse(input: ReadonlySourceSnapshot, context: ParseContext): Promise<ParsedDocument>;
}
```

`ReadonlySourceSnapshot` 由宿主完成路径约束、大小检查和哈希验证，再提供有界字节读取；插件不重新读取不受控路径。`ParseContext` 只有取消、限额和诊断能力，没有 Agent Store、模型或执行设备权限。受信插件可以在进程内运行，但这不是 OS 沙箱；需要隔离的解析器以后可用子进程适配。

第一期内置 Markdown、UTF-8 text、JSON；JSON 只保留通用结构和 JSON Pointer，不推断业务。PDF、DOCX、XLSX 等分别做明确的格式适配和验收，不宣称已支持所有文件。未知格式登记为 unsupported，保留原件和诊断，不假装成功索引。

SAM/SMP 解析从 `src/wiki/file-index/{sam,reference,...}` 提取到独立 workspace 包，通过 exports 注册。包只负责只读解析与证据投影，不导入 Agent Store，也不承接模板生成、保存或执行。原有版本、单位、字段覆盖回归测试随解析器迁移。

### 6.2 模型增强可选且独立

- 索引文本本身即可检索；配置 API key 不是建立普通资料库的条件。
- 显式启用增强后，可生成摘要、标签或某一 schema 的结构化事实。
- 模型调用使用通用 `complete` 请求；提示词和校验属于增强任务，不属于模型网关。
- 记录输入版本、模型配置指纹、提示词/解析版本和引用；截断/失效引用不发布。
- 增强失败不删除确定性解析结果。搜索返回原文与派生内容时清楚区分，不自动把派生摘要排在来源证据前面。
- 用户手写的推荐说明就是普通文档，照常索引，无需为了进入推荐查询再调用模型。

## 7. 索引、更新和一致性

1. 添加/刷新创建本地构建任务，固定来源范围和解析器版本。
2. 扫描并形成候选清单，使用 `contentHash + parserVersion + optionsHash` 判断复用；mtime/size 只能作为扫描优化，不单独作为内容身份。
3. 按文件读取固定版本、解析与分块，写入 staging；单文件与总量有界，可取消。
4. 更新 FTS 与结构化属性索引，在事务中切换发布的 generation。
5. 完成后发资料失效通知，界面 GET 新快照；查询过程不隐式重建。

来源不可访问、扫描不完整或发布失败时保留上一完整版本，不将“目录打不开”当成“全部文件已删除”。单文件解析失败可以在任务报告中展示，但第一期不静默发布缺少失败文档的替代版本；支持的文件子集要通过明确范围重新构建。

取消和进程中断丢弃未发布 staging；已发布快照保持可用。跨来源更新可独立发布，但一次搜索使用固定 generation 集合，结果含版本信息。

搜索采用本地 SQLite FTS5 + 确定性排序，中文分词策略需要专门回归测试。第一期不依赖向量库或模型检索。将来加入 embeddings 属于可选索引实现，不能改变来源、引用、读取和权限协议。

区分三种状态：索引中的内容版本、最近一次观察到的来源状态、原件当前是否已核验。一次普通查询不会扫描外部目录，因此不能宣称“当前原件仍一致”。内置离线资料包明确显示 snapshot-only。

## 8. 工具与 API

### 8.1 Agent 的 `wiki` 工具

建议保留一个工具，动作统一为：

- `catalog`：返回可用资料集、格式、扩展字段及当前索引状态，分页/有界返回。
- `search`：query、collection/source 范围、经过注册校验的字段筛选、limit/cursor。
- `read`：document/version/unit ID 或本次检索返回的引用、范围/cursor、字节预算。

不再让 `query` 暗指“推荐知识”。基于资料回答由 Agent 组合搜索、阅读和模型推理完成，Wiki 查询自身不启动模型。原文阅读与派生内容阅读使用相同引用封套，标明 representation/provenance。

`read` 不接受任意本地绝对路径；只读取已登记且在当前授权范围内的资料。结果过大提供可继续阅读的范围/游标和明确截断信息，不静默删除关键配置后声称返回了完整资料。

通用 Wiki 不再要求先加载任意 Skill 才能读资料。权限由已配置的资料范围和工具策略决定；领域任务仍应加载相关 Skill 来解释资料。当前 loaded-skill 前置是旧契约，实施时必须同步修改工具规范、提示词和测试，不能只删检查。

### 8.2 管理面与只读面

| 目标 API                       | 用途                        |
| ------------------------------ | --------------------------- |
| `GET /wiki/catalog`            | 资料集、字段目录与能力      |
| `GET /wiki/sources`            | 来源状态、上次构建与错误    |
| `POST /wiki/search`            | 有界结构化检索请求，只读    |
| `GET /wiki/documents/:id`      | 元数据与可读版本            |
| `POST /wiki/read`              | 按引用和范围读取，只读      |
| `POST /wiki/sources`           | 显式登记受允许的来源        |
| `POST /wiki/builds`            | 对选定来源创建刷新/增强任务 |
| `GET /wiki/builds/:id`         | 进度与逐项诊断              |
| `POST /wiki/builds/:id/cancel` | 取消未发布工作              |

删除来源只解除索引关联，不删除关联目录里的原件；应用管理的导入副本按单独保留策略清理。来源修改使用 revision/ETag 避免陈旧保存覆盖。导入、更新和删除是管理动作，不自动暴露给聊天模型。

桌面通过有范围的原生命令选择文件/目录和传输导入内容，WebView 不直接读取文件系统或访问 SQLite。内置来源与用户来源可以同时搜索，而不是互相替代。

CLI 最终收敛成同一服务的 `wiki add/list/refresh/search/read/status` 命令族；语法和 HTTP 合同在实施阶段一起定版。

## 9. 实施顺序与验收

### A. 冻结统一契约

定义 Source/DocumentVersion/Unit/Reference、Parser 和搜索/阅读响应；建立 Wiki 自己的仓储和组合接口。验收：协议中没有 SAM、厂家或仪器字段；AgentRunner 不 import Wiki 实现。

### B. 完成普通文档端到端

MD/TXT/JSON、目录接入、本地解析、FTS、引用阅读、刷新和取消。验收：未配置模型 key，混合格式目录仍可添加、搜索与阅读；修改/删除/取消/不可访问来源有确定行为。

### C. 接入领域插件并导入既有资产

提取 SAM 解析包，把现有推荐原文和模板快照导入统一协议。验收：普通文档与模板可同时命中；原始版本、单位、模式、引用和不可核验状态不丢失；旧快照转换有数量/哈希/字段覆盖报告。

### D. 统一工具、API、CLI 与桌面

切换查询/阅读契约与来源设置，删除旧两套运行路径；更新 `llm.txt`、Skill 引用方式、配置说明和打包收集器。验收：用户只做一次添加和刷新，无需维护编译 JSON；外部来源不会屏蔽内置资料。

### E. 可选增强与发布

最后接入显式模型增强、资料包构建/校验/离线加载。验收：增强失败不损坏基础索引；截断、来源不匹配与版本过期不发布；索引升级不能仅凭文件哈希错误复用旧解析。

第一批回归必须涵盖跨格式检索、中文查询、稳定引用、源更新/删除、失败发布回滚、取消、重复导入、损坏资料包、解析器升级、路径约束、超限文件、凭据/原始内容不进入诊断、离线快照与当前来源核验的区别。

## 10. 与正在进行的基座重构的衔接

参考用户指定的 `llm_wiki` 后，目标进一步明确为“原始资料 + 持久化 Wiki 页面 + 检索索引”。统一检索不等于将 Wiki 降格成缓存：页面要记录来源依赖、版本和维护变更，支持 Markdown 导出；索引只负责发现和读取。相关实现取舍和阶段划分见 [wiki-progress.md](./wiki-progress.md)。

基座只接收通用工具调用结果、动态上下文保留规则和有界证据；无需识别 Wiki 的数据分类。新的 Wiki 通过独立服务适配进入工具目录与应用管理面。

本轮基座已将模型提取移到 Wiki 任务调用通用 `complete` 的路径，并把运行循环移到 `AgentRunner`；这为替换资料服务提供边界。现有 Wiki ToolContext 和应用维护入口仍是过渡适配，在本设计实施时替换。不要为了保留旧 API，把领域字段重新塞进通用 Runner、模型网关或证据仓储。
